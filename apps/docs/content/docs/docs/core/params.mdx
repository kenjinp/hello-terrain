Terrain configuration in Hello Terrain is built on top of the `Param` system from `@hello-terrain/work`.

The core terrain graph in `@hello-terrain/three` exposes a shared set of params such as `rootSize`, `maxLevel`, `elevationScale`, and `terrainFieldFilter`. Higher-level APIs like `@hello-terrain/react` map their props and options onto these same graph inputs.

## Terrain Params

| Param | Type | Default | What It Controls |
|-------|------|---------|------------------|
| `rootSize` | `number` | `256` | The world-space size of the root terrain region. Larger values cover more world space before subdivision. |
| `origin` | `{ x: number; y: number; z: number }` | `{ x: 0, y: 0, z: 0 }` | The world-space origin of the terrain root. This offsets the terrain surface and related bounds calculations. |
| `maxLevel` | `number` | `16` | The maximum quadtree subdivision depth. Higher values allow finer terrain detail close to the tracked origin. |
| `maxNodes` | `number` | `1024` | The maximum number of active terrain tiles that can be rendered and processed at once. |
| `innerTileSegments` | `number` | `61` | The vertex resolution inside each terrain tile before skirts are added (effective edge vertex count is `innerTileSegments + 3`, so the default is a `64×64` tile grid). Higher values increase per-tile detail and cost. |
| `skirtScale` | `number` | `100` | The length of the downward skirt geometry used to hide cracks between terrain LOD levels. |
| `elevationScale` | `number` | `1` | A multiplier applied to the sampled elevation values, controlling the vertical exaggeration of the terrain. |
| `radius` | `number` | `1000` | The sphere radius used by the cube-sphere projection. Ignored by flat topologies. See [Cube-Sphere Planet](/docs/examples/cube-sphere). |
| `elevationFn` | `ElevationCallback` | `() => float(0)` | The terrain height function. See [Elevation Function](/docs/core/elevation-function). React exposes this as the `elevation` option. |
| `cameraView` | `{ cameraOrigin; viewProjectionMatrix }` | origin at `{0,0,0}`, identity matrix | Per-frame camera origin and view-projection matrix for LOD and frustum culling. Uses equality gating so unchanged frames stay cheap. |
| `residencyAnchors` | `TerrainResidencyAnchor[]` | `[]` | World-space support regions that keep terrain data resident even when render culling hides those tiles. |
| `lodCriteria` | `LodCriteria` | `{ mode: "distance", distanceFactor: 1.5 }` | How subdivision decisions are made (distance vs screen-space LOD). |
| `topology` | `Topology` | `null` | The terrain topology that defines tile layout, bounds, and the injected [surface projection](/docs/core/projection). Leave it unset for the default flat topology, or pass `createInfiniteFlatTopology` / `createCubeSphereTopology` / `createTorusTopology`. See [Topology Types](/docs/core/topology). |
| `terrainFieldFilter` | `"nearest"` \| `"linear"` | `"linear"` | The sampling filter used when reading terrain field textures. Use `linear` for smoother interpolation or `nearest` for exact texel reads. Terrain fields use `rgba16float` with per-tile normalized elevation in `.r` (denormalized at sample time using per-tile pack bounds). |

## Where These Params Apply

These params are part of the core terrain graph.

- In `@hello-terrain/three`, you can import the param refs directly and set them on a graph.
- In `@hello-terrain/react`, options like `rootSize`, `maxLevel`, `elevation`, and `terrainFieldFilter` are translated onto these same graph params.
- Advanced integrations can add their own params and read them inside custom tasks.

## Built On `@hello-terrain/work`

The terrain graph uses `param()` from `@hello-terrain/work` to define reactive inputs:

```ts
import { param } from "@hello-terrain/work";

export const rootSize = param(256).displayName("rootSize");
export const maxLevel = param(16).displayName("maxLevel");
```

When a task reads one of these params with `get(paramRef)`, the graph tracks that dependency and marks downstream tasks dirty whenever the param changes.

## Using Terrain Params Directly

In lower-level `@hello-terrain/three` code, you can set core terrain params on a graph yourself:

```ts
import { terrainGraph, rootSize, maxLevel, elevationScale } from "@hello-terrain/three";

const graph = terrainGraph();

graph.set(rootSize, 4096);
graph.set(maxLevel, 6);
graph.set(elevationScale, 200);
```

This takes graph-local ownership of those params, which is the idiomatic `@hello-terrain/work` model for multi-instance graphs.

## Creating Your Own Params

You can define your own params with `@hello-terrain/work` and use them alongside the built-in terrain params.

```ts
import { graph, param, task } from "@hello-terrain/work";
import { rootSize, maxLevel } from "@hello-terrain/three";

const scatterCount = param(1024).displayName("scatterCount");

const debugTask = task((get, work) => {
  const size = get(rootSize);
  const level = get(maxLevel);
  const count = get(scatterCount);

  return work(() => ({ size, level, count }));
}).displayName("debugTask");

const g = graph()
  .add(debugTask)
  .set(rootSize, 2048)
  .set(maxLevel, 8)
  .set(scatterCount, 2048);
```

This is useful for custom scatter systems, debug overlays, analysis tasks, or any terrain-adjacent feature that should participate in the same graph lifecycle.

## Shared Params vs Graph-Owned Params

`@hello-terrain/work` supports both shared params and graph-owned params:

- A plain `param()` stores a shared value.
- `graph.set(paramRef, valueOrCallback)` gives one graph its own local value for that param.
- `graph.reset(paramRef)` resets a graph-owned param back to its baseline for that graph.

Hello Terrain uses graph-owned params so multiple terrain instances can coexist without leaking values into each other.

## Equality-Gated Params

Some params define an `equals` comparator when created with `param(initial, { equals })`. When you `graph.set()` a value that `equals` considers unchanged, the graph stores the value but **does not** bump the param version or invalidate downstream tasks. This keeps per-frame `set()` + `run()` loops cheap.

`cameraView` and `residencyAnchors` ship with hysteresis-aware `equals` functions. Push fresh values every frame; the graph skips work when movement is below the threshold.

## Per-Frame Loop (Vanilla)

You own the render loop. Each frame, set dynamic params and call `run()`:

```ts
import {
  cameraView,
  createInitialCameraView,
  readCameraView,
  residencyAnchors,
  terrainGraph,
  terrainTargets,
} from "@hello-terrain/three";

const graph = terrainGraph();
const cameraScratch = createInitialCameraView();
const targets = terrainTargets();

useFrame(async ({ camera, gl }) => {
  graph.set(cameraView, readCameraView(camera, cameraScratch));
  graph.set(residencyAnchors, getAnchors());
  await graph.run({ targets, resources: { renderer: gl } });
});
```

`graph.run()` coalesces overlapping calls when inputs are unchanged and preempts in-flight runs when inputs change.

## React Mapping

In `@hello-terrain/react`, static shape options map directly to graph params. Dynamic inputs are grouped:

```tsx
const terrain = useTerrain({
  rootSize: 4096,
  maxLevel: 6,
  elevation,
  culling: {
    camera: cullingCamera,
    getCameraOrigin,
    originHysteresis: 0.35,
  },
  residency: {
    getAnchors: getResidencyAnchors,
    hysteresis: 0.25,
  },
  lod: { mode: "distance", distanceFactor: 1.4 },
  pipeline: { compute: true, readback: true, gpuSpatialIndex: true },
});
```

- `elevation` maps to `elevationFn`.
- `culling.camera` / `culling.getCameraOrigin` drive `cameraView` each frame.
- `residency.getAnchors` drives `residencyAnchors` each frame.
- `lod` maps to `lodCriteria`.
- `pipeline` selects which tasks `run()` targets via `terrainTargets()`.
- `tasks` adds extra `@hello-terrain/work` tasks to the graph.
