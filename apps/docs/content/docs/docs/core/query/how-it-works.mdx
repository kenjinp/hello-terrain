---
title: Snapshot architecture
description: How production, CPU readback, and query reconstruction stay coherent
---

The runtime publishes rendering and CPU queries separately. Each publication carries instance, configuration, content, layout, production, and accepted-edit identifiers. A newer render revision may coexist with an older CPU snapshot.

## Production and publication

1. Configuration acceptance copies data and validates dimensions, capacity, range, and LOD settings.
2. A candidate backend slot selects leaves, evaluates elevation, computes bounds and normals, and prepares render nodes.
3. Successful submission publishes a complete render record. Preparation failure preserves the last good record.
4. A requested readback submits elevation and bounds copies before awaiting either mapping. It captures the matching tile index and query interpretation.
5. Completion publishes one CPU record. Failed transfers leave the previous successful record available.

The backend reuses retired candidate slots. CPU records exposed to readers are independent copies, never reused as transfer destinations. Snapshot leases retain their data across resource replacement and disposal.

## Sampling

CPU position queries locate a resident leaf and interpolate its raw float32 elevation grid. Flat normals use local gradients; curved surface normals use the projection's CPU surface operations. GPU curved normals use datum derivatives and local height differences to avoid subtracting independently rounded planet-sized positions.

The render field stores normalized elevation and geometric normals, using `rgba16float` by default. Per-tile decoding bounds restore elevation before scale. CPU and GPU storage and normal approximations differ, so bit-identical reconstruction is not promised. `rgba32float` helps isolate packing error during validation.

Mesh triangles are another approximation of the field. A bilinear CPU sample need not lie exactly on the rasterized triangle surface. Raycasts report incomplete searches rather than claiming unsupported exactness.

## Invalidation and retention

Changing elevation content must advance its accepted edit even when the camera and tile layout remain stationary. Captured mutable inputs are not automatically observed; use explicit invalidation or managed source edits.

Appearance-only edits reuse geometry and do not trigger geometry readback. A map used by both appearance and elevation declares both dependencies.

Readback can be automatic, manual, or disabled. Requests target an accepted edit or newer. Retention admission rejects requests when pinned records exhaust the configured budget; release leases before retrying. CPU snapshot availability does not imply coverage of every point.
