description: Use published terrain values in materials and distinguish source evaluation

For shading the terrain itself, use the published `materialContext`. It provides elevation and normals without searching the resident tile index or re-evaluating the elevation callback.

```tsx
<Terrain elevation={elevation} elevationRange={{ min: -1, max: 1 }}>
  {({ positionNode, materialContext }) => (
    <meshStandardNodeMaterial
      positionNode={positionNode}
      colorNode={materialContext?.elevation.smoothstep(0, 1)}
    />
  )}
</Terrain>
```

Use [source mappings and textures](/docs/core/nodes/materials) for control maps and fine detail. Appearance sampling is evaluated in the material; it is not automatically baked or copied to CPU.

## Resident samples and source evaluation

The backend distinguishes two operations:

- **Resident sampling** reconstructs the field available in the published render resources. It has finite coverage, resolution, and packing precision.
- **Source evaluation** runs the authored TSL expression at a datum location. It may be more expensive and has the expression's own precision and sampling limits.

Source evaluation is not an exact-height mode. Compute and fragment texture sampling can use different mip policies. Production-only regional coordinates are unavailable in source evaluation contexts that do not supply them.

The current runtime does not expose a general revision-managed GPU attribute sampler for arbitrary off-mesh objects. Use [CPU snapshot queries](/docs/core/query/terrain-query) for supported synchronous gameplay sampling. GPU scatter extensions must explicitly manage resident coverage, source inputs, and resource lifetime; a texture lookup alone does not establish those contracts.
